# Adding a Generator to rakitin

> Tutorial for rakitin v2.0.0. Everything below matches the current APIs:
> `lib/safety.js`, `lib/deps/manifest.js`, `lib/commands/{shared,add}.js`,
> `bin/rakitin.js`, and the Jest harness in `tests/setup.js`.
>
> Worked example: a new headless generator used as
> `rakitin add service audit-log --json`.

---

## 0. Design decisions before you type

Modern generators are **headless-first**: an interactive menu may *wrap* them,
but the core generation logic must work purely from arguments because CI runs,
AI agents (`--json`), and `--yes` unattended mode depend on it.

Decide up front:

| Question | Convention |
| --- | --- |
| Where does output go? | Conventional locations from `getPaths()` (`app/shared`, `app/modules/<name>/…`). Never `process.cwd()` guessing games. |
| Does output need npm packages? | If yes → register a kind key in `KIND_DEPENDENCIES` (step 3), never install inline. |
| Interactive behavior | Core function takes everything as parameters; prompts happen ONLY when the caller did not supply values and `context.yes` is false. |
| Overwrite policy | Never overwrite silently — write-if-absent, `.bak` via `overwriteWithBackup` when regeneration is required. |

Rule of thumb taken from existing commands (`addModule`, `addMiddleware`): the
**non-interactive core function signature returns a summary object**, and the
interactive wrapper only fills gaps before delegating.

## 1. Build the non-interactive core function

Create `lib/generator/service/service.js`. Requirements:

- Signature accepts plain data (name + options), performs NO prompting.
- Resolves paths lazily via `getPaths()` **at call time** so `--cwd` /
  test-cwd overrides are honored.
- Derives every name variant from `lib/naming.js` (`getModuleVariants`,
  `toIdentifier`) — never hand-rolled case conversion.
- Returns `{ created, createdFiles?, skipped?, kind }`.

```js
// lib/generator/service/service.js
const path = require("path");
const inquirer = require("inquirer");
const { getPaths } = require("../../constants");
const { writeFileIfNotExistsSafe } = require("../../safety");
const { getModuleVariants } = require("../../naming");
const { validateModuleName } = require("../shared/validation-utils");

function serviceTemplate(variants) {
  return `// ${variants.pascal} Service - generated by rakitin

class ${variants.pascal}Service {
  constructor() {
    this.items = [];
  }

  async getAll() {
    return this.items;
  }

  async add(item) {
    this.items.push(item);
    return item;
  }
}

module.exports = new ${variants.pascal}Service();
`;
}

/**
 * Generate a shared service file at app/shared/services/<kebab>.service.js.
 * Headless core - safe to call from CLI flags, recipes, or tests.
 * @param {string} name User-provided service name ("audit log", "AuditLog", ...).
 * @returns {{created: boolean, createdFiles: string[], skipped: string[], kind: string}}
 */
async function createService(name) {
  const validation = validateModuleName(String(name ?? "").trim());
  if (!validation.isValid) throw new Error(validation.message);

  const variants = getModuleVariants(name);
  const p = getPaths(); // lazy snapshot: resolved NOW, honors cwd overrides
  const filePath = path.join(
    p.sharedPath, "services", `${variants.kebab}.service.js`
  );

  const res = writeFileIfNotExistsSafe(filePath, serviceTemplate(variants));
  const rel = path.relative(process.cwd(), filePath);

  return res.written
    ? { created: true, createdFiles: [rel], skipped: [], kind: "service:core" }
    : { created: false, createdFiles: [], skipped: [rel], kind: "service:core" };
}

/** Interactive wrapper reusing the same core (menu keeps working headless-free). */
async function createServiceInteractive() {
  const { serviceName } = await inquirer.default.prompt([
    {
      type: "input",
      name: "serviceName",
      message: "Nama service:",
      validate: (v) => Boolean(String(v).trim()) || "Nama wajib diisi",
    },
  ]);
  return createService(serviceName);
}

module.exports = { createService, createServiceInteractive };
```

Why this shape works everywhere downstream: `printResult` accepts
`createdFiles` / `skipped` arrays directly, `--dry-run` support came free
because the write went through the safety layer, and the returned object
documents intent without hidden I/O side effects beyond that single write.

## 2. Route ALL writes through the safety layer

There are exactly two sanctioned write helpers (both auto-plan-aware):

```js
const { writeFileIfNotExistsSafe, overwriteWithBackup } = require("../../safety");
// legacy alias: utils.writeFileIfNotExists -> safety.legacyWriteIfAbsent
```

| Helper | Behavior on disk | In dry-run plan |
| --- | --- | --- |
| `writeFileIfNotExistsSafe(filePath, content, {dryRun}?)` | Creates parents recursively, writes only when absent; returns `{ written, skipped: "exists"\|null }` | Records `{ op: "create", path }`, writes nothing |
| `overwriteWithBackup(filePath, content, {dryRun}?)` | Copies previous content to `<file>.bak`, then overwrites (or creates fresh) | Records `{ op: "backup+overwrite", path }` |

Never call bare `fs.writeFileSync` against user-project files in a generator:
it bypasses `--dry-run`, skips backups, and breaks the "existing files are
never silently clobbered" guarantee that `doctorCommand` advertises.

For router-region edits specifically, keep lines OUT of `app/routes/index.js`
in this example (services aren't wired into Express), but when a future
generator must touch the router see `buildRoutesContent(existing, routeLines)`
— markers `/* rakitin:routes:start */ … /* rakitin:routes:end */` and the pure
`{ content, action }` contract.

## 3. Register dependencies in `KIND_DEPENDENCIES`

If your output imports packages the project might not have, declare them in
`lib/deps/manifest.js`. Suppose our service supports a Prisma-flavored variant
and a Mongoose variant:

```diff
--- a/lib/deps/manifest.js
+++ b/lib/deps/manifest.js
@@ -25,6 +25,9 @@ const KIND_DEPENDENCIES = {

   "middleware:auth": ["jsonwebtoken"],
+  // Service family (rakitin add service ...)
+  "service:core": [],
+  "service:prisma": ["@prisma/client", "prisma"],
+  "service:mongoose": ["mongoose"],

   "util:any": [],
```

That single registration makes several things true automatically:

1. `resolvePackagesForKinds(["service:prisma"])` dedupes against any other kinds
   requested in the same run (e.g. `module:prisma`) so packages install ONCE.
2. `ensureDependencies(kinds, { silent, pm })` installs only what's missing,
   using the package manager detected by `installer.getPackageManager()`
   (lock-file based: pnpm/yarn/bun/npm).
3. Unknown kinds surface a warning instead of silently doing nothing.

In the command wrapper you'll invoke it awaited (see next section) — installing
inline or forgetting the await is exactly the bug class the manifest was built
to remove.

## 4. Wire into the CLI dispatch (two switches)

### 4a. Command layer: `lib/commands/add.js`

Add a case in `addCommand`'s `switch (thing)` plus a thin headless adapter that
fills prompts only when allowed:

```js
// lib/commands/add.js (relevant excerpts)
const { createService } = require("../generator/service/service");
const { ensureDependencies } = require("../deps/manifest");

async function addCommand(thing, name, context) {
  switch (thing) {
    case "module":
      return addModule(name, context);
+   case "service":
+     return addService(name, context);
    case "middleware":
      return addMiddleware(name, context);
    // ...
  }
}

async function addService(name, context) {
  let serviceName = name;
  if (!serviceName && !context.yes) {
    ({ serviceName } = await inquirer.default.prompt([
      { type: "input", name: "serviceName", message: "Nama service:" },
    ]));
  }
  if (!serviceName) throw new Error("Nama service wajib ada.");

  const result = await createService(serviceName);

  // Manifest-driven deps: never dangling imports, never double installs.
  if (result.created && context.install && result.kind !== "service:core") {
    await ensureDependencies([result.kind], { silent: !!context.json, pm: context.pm });
  }

  return {
    ...result,
    nextSteps: result.created
      ? [
          // Concrete, copy-pasteable tip built from what actually got written.
          `Impor service di controller Anda: require('../${result.createdFiles[0].replace(/\.js$/, "")}')`,
        ]
      : ["File sudah ada - hapus manual bila ingin dibuat ulang"],
  };
}
```

### 4b. Bin dispatcher: `bin/rakitin.js`

The yargs declaration `"add <thing> [name]"` routes through `runAdd(argv)`,
whose final `else` branch simply delegates:

```js
// bin/rakitin.js (runAdd excerpt - no edit needed for normal cases)
} else {
  const { addCommand } = require("../lib/commands/add");
  result = await addCommand(argv.thing, argv.name, ctx);
}
```

So your new thing automatically inherits the shared prelude: `buildContext`
(flags normalized), `enterProjectRoot(ctx)` (`chdir` to `--cwd`),
`enableJsonMode()` for `--json`, and `safety.beginPlan()` for `--dry-run`, with
`safety.getPlan()` merged into `printResult`. Only reach into `runAdd` itself
when your generator needs special flag handling beyond those globals (like
`util`'s rich kind menu).

Also update the two surfacing points users look at:

- The `thing` union in the `add` command description string in
  `bin/rakitin.js` (`Generate komponen (module|…)`).
- The `CATALOG` array in `lib/commands/info.js` so `rakitin list` shows the
  generator and its tier (`basic` / `intermediate` / `advanced`).

## 5. Declare env keys (the `mergeEnvExample` pattern)

When generated output reads configuration from `.env`, do NOT write `.env`
directly and do NOT clobber a user's `.env.example`. Follow the established
pattern from `lib/commands/recipe.js` (`mergeEnvExample`):

- Target file: `.env.example` only.
- Append each `KEY=value` line once — skip keys whose `KEY=` prefix is already
  present anywhere in the file.
- Fresh file: create it with just the block; existing file: append a marker
  comment then the missing lines.

If your generator introduces environment knobs, list them as a named constant
next to the generator and reuse the same semantics:

```js
const SERVICE_ENV_KEYS = ["SERVICE_MAX_ITEMS=100"];
// append-if-missing into .env.example, mirroring recipe.js mergeEnvExample()
```

Keep the constant adjacent to the template that consumes those variables so
future edits stay paired. (Today `mergeEnvExample` is a private helper inside
`recipe.js`; mirroring it locally is acceptable for one call site — lifting it
into a shared util is welcome cleanup, done separately.)

## 6. Add `nextSteps` strings

Every command result ends with an actionable 🧭 block rendered by
`printResult`. Guidelines observed in existing commands:

- Make each step copy-pasteable (a real command or code reference).
- First step should tell the user how to verify or USE what was generated.
- Keep results ordered: most important action first.
- Numbers come free — `printResult` renders `1. 2. 3.`.

Good examples from the codebase to calibrate tone and specificity:
`buildModuleNextSteps()` in `lib/commands/add.js`,
auth/swagger/docker recipes' `nextSteps` arrays in `lib/commands/recipe.js`.

## 7. Test requirements (hard gates)

A generator PR is complete only when all three assertions exist. Location:
either a dedicated suite (`tests/lib/generator/service.test.js`) AND/OR a
policy gate in `tests/regression/`. Use the real fs sandbox — `tests/setup.js`
already gives each suite a private mkdtemp dir exposed as `global.tempDir`, with
`process.cwd` pointing at it.

```js
// tests/lib/generator/service.test.js
const path = require("path");
const vm = require("node:vm");
const fs = require("fs-extra");
const safety = require("../../lib/safety");
const { createService } = require("../../lib/generator/service/service");

describe("createService", () => {
  afterEach(() => safety.resetPlan());

  test("generated artifact compiles via vm.Script (codegen gate)", async () => {
    const r = await createService("audit log");
    const file = path.join(global.tempDir, r.createdFiles[0]);
    expect(fs.existsSync(file)).toBe(true);
    expect(() => new vm.Script(fs.readFileSync(file, "utf8"))).not.toThrow();
  });

  test("--dry-run equivalent: beginPlan records intent, disk untouched", async () => {
    safety.beginPlan();
    try {
      const r = await createService("pricing");
      expect(r.created).toBe(false);
      expect(safety.getPlan()).toEqual([
        {
          op: "create",
          path: path.join(global.tempDir, "app", "shared", "services", "pricing.service.js"),
        },
      ]);
      expect(fs.existsSync(path.join(global.tempDir, "app"))).toBe(false);
    } finally {
      safety.resetPlan();
    }
  });

  test("idempotent: second run skips instead of overwriting", async () => {
    const first = await createService("billing");
    expect(first.created).toBe(true);

    const second = await createService("billing");
    expect(second.created).toBe(false);
    expect(second.skipped[0]).toContain("billing.service.js");
    const stillOriginal = fs.readFileSync(
      path.join(global.tempDir, second.skipped[0]), "utf8"
    );
    expect(stillOriginal).toContain("class BillingService");
  });
});
```

Notes on why each gate exists:

- **`vm.Script` compile check** — protects against syntax regressions in
  templates (the standing rule across `tests/regression/p0-bugfixes.test.js`
  and `tests/lib/generator/*`). Fragments referencing user-project modules may
  strip/substitute `require(...)` first, as `arch.test.js` does with its
  `stripRequires` helper; your template above needs nothing removed because it
  has no requires.
- **Dry-run via `beginPlan`/`getPlan`/`resetPlan`** — proves you routed writes
  through the safety layer rather than raw fs (a bare `writeFileSync` would
  either touch disk during this test or record no plan entries).
- **Idempotency assertion** — guards the write-if-absent contract
  (`skipped: "exists"`), i.e. rerunning `rakitin add service x --yes` twice
  leaves user edits intact.

Run the suite: `npx jest tests/lib/generator/service.test.js`.
